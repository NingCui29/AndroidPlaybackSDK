# H01～H04　Android 视频硬解与软解回退设计

H01～H04 已有实现。D01 既有构建完成了正常硬解和故障注入，当前候选的码流适配、顺序恢复缓存及待执行真机用例按构建摘要记录。H01 与 H02 可在 Q01 后并行，H03 依赖两者，H04 依赖 H03 与 S04。音频继续使用 S01，音画调度、定位落点及停止释放沿用[S03～S05](11-software-playback.md)。[硬解真机验收表](14-hardware-device.md) · [当前实测](21-implementation.md)

## H01　候选选择与实际后端识别

1. 从 I03 读取轨道编码、profile、level、位深、可见尺寸、编码尺寸及已知帧率。区分未知与不支持。枚举匹配 MIME 的普通解码组件，排除编码器及要求安全输出的专用组件；本阶段验证非 DRM、SDR 输入。
2. 查询候选声明的 profile/level、尺寸、尺寸对齐及尺寸与速率组合。能力预筛后按组件名创建，分别记录创建、配置、启动、首次有效输出四个阶段。诊断同时保留轨道参数、候选淘汰原因、组件名称和实际输出格式。成功启动仍需首帧与持续播放证据。
3. API 29 起读取平台硬件加速、软件实现等分类，并记录名称及别名；平台分类为设备报告。旧 API 结合已验证的设备固件与组件映射，无法确认时标记“未知”。仅硬解要求可确认的硬件类型；自动模式对未知组件的默认选择为待确认策略，应如实标记实际分类。[Android MediaCodecInfo](https://developer.android.com/reference/android/media/MediaCodecInfo)
4. 自动策略对支持的硬件候选设尝试上限，耗尽后进入 H04；仅软解直接进入 Q01 路径；仅硬解返回候选与失败阶段。资源不足单列，可用双实例复验。一次轨道失败记录限定于该会话及配置，避免永久屏蔽整个机型。

**验收**：同一设备、同一样本跑三种策略，对照能力查询、实际组件和首帧记录。旧 API 上分类未知时验证仅硬解结果；缺少硬件能力的组合单列，不能算作硬解成功。

## H02　H.264 与 HEVC 码流适配

| 输入 | 初始化数据 CSD | 提交前检查 |
|---|---|---|
| H.264 / AVC | 从 avcC 或流内参数集提取 SPS、PPS；采用 MediaFormat 配置方式时分别置于 csd-0、csd-1，每个参数集带四字节起始码 | 按配置记录给出的 NAL 长度字段宽度解析长度前缀；已是 Annex B 的输入识别起始码，不再次转换 |
| HEVC / H.265 | 从 hvcC 或流内参数集取得 VPS、SPS、PPS；按顺序带起始码串接到 csd-0 | 保留有效参数集及其关联，验证每个长度在当前包范围内；遇到截断数据报告轨道、包位置和失败阶段 |

适配器按访问单元组织输入。若分包边界与访问单元不一致，在有界缓冲中用解析器组装，不能假定一个 NAL 就是一帧。按解码顺序送入，时间戳按流 time base 转为微秒 PTS，保留原始 PTS/DTS 供比对。含 B 帧的流不得按 PTS 提前排序。时间戳缺失按 S03 策略记录估算；无法建立可靠时间轴时明确报告。

配置时已传入 CSD 的组件由平台在启动时提交，正常启动不再显式重复注入。启动后、首次输出或格式变化前发生 flush 时，要按平台规则恢复 CSD；完整重建则重新配置。若只在流内出现参数集，先限量等待可用参数与随机访问点。参数集或分辨率变化时更新配置版本；能适应的组件按平台要求在可解码边界交付新参数，超出能力则重建。适配输出独立持有缓冲，保留原始压缩包供 FFmpeg 回退。[Android MediaCodec 的 CSD 约定](https://developer.android.com/reference/android/media/MediaCodec)

**验收**：对 V01、V03、V04、V10、V11 独立核对参数集、访问单元次序、输入 PTS 和显示帧号。复验初始化后立即定位、参数在流内、合法长度字段变体和截断包。遇到输入损坏应保留根因，即使随后另一个后端也失败。

## H03　Surface 直出与时序

以有效 Surface 配置视频解码器。压缩访问单元经过输入缓冲，解码后的输出缓冲直接提交到 Surface。视频工作线程独占 codec 生命周期；每个有效输出索引在所属实例及版本内交付或丢弃一次，flush 或重建后丢弃过时索引。

调度使用输出 PTS 与 S03 媒体时钟计算显示期限，转换到系统单调时间后定时提交。限制提前提交的时间窗口，避免暂停或定位时仍有一串旧帧等待显示。暂停、解绑和释放先停止新提交，再处理在途输出；不得声称已经提交给显示系统的帧可以撤回。重绑时校验 Surface 版本，兼容时切换输出，其他情况从可解码点重建。旧 Surface 完成解绑后不再有新提交。

输出格式变化时记录编码尺寸、可见裁剪、像素宽高比与旋转。根据后端实际应用的变换计算显示布局，保证旋转仅执行一次。分别记录首个解码输出、首次提交、设备首个可见画面；无 Surface 的音频播放仍可推进。完整双后端输出重建回归归 L02。

**验收**：检查旋转标尺、动态尺寸、暂停恢复、定位及换 Surface。用画面采集确认首帧方向、边缘、暂停位置和恢复后的帧号；内部提交记录用于定位渲染前后延迟。

## H04　失败分类与回退事务

| 失败时机 / 输入能力 | 自动模式动作 | 终止或恢复的证据 |
|---|---|---|
| 创建、configure 或 start 失败 | 保存原错误，释放部分创建的组件；使用保留的流参数和原始包准备软件解码器 | 记录失败阶段、软解器及首个有效输出；音轨和用户播放意图保留 |
| 已送包、尚无首帧 | 区分暂停、无输出目标、正常预滚和真实超时；确认失败后按可定位性恢复已消费数据 | 记录已提交包范围、最后可解码点及首次输出等待耗时 |
| 播放中失败，可定位输入 | 保存实际媒体位置和播放意图；暂停输出并使旧时间轴失效；按 S04 定位到目标前随机访问点，软解预滚，裁掉目标前 PCM，重新建立时钟 | 记录故障前位置、恢复目标、软解首个显示帧、音频恢复点与偏差；暂停中的恢复保持暂停 |
| 播放中失败，顺序输入 | 若缓存覆盖有效随机访问点至当前包且参数完整，按解码顺序重放视频；否则丢弃不可解码的中间图像，等待下一个有效入口。建议音频持续，恢复时视频追到当前音频时钟 | 单列遮屏时长、缓存字节、等待时长及恢复偏差；缓存不足、无下一关键帧或超时则结束恢复并报告错误 |
| 仅硬解 / 软解也失败 | 仅硬解按原策略结束；自动模式保留硬解首因和软解失败原因，按契约报告终态 | 后端选择事件与最终状态一致，不循环回硬解 |

可恢复的输出目标丢失优先走 H03。用户 stop、release、切源优先于恢复，禁止新会话接收旧恢复事件。回退期间收到新的 seek，以最新目标和时间轴版本为准。只有软件后端交付有效输出后才发“恢复成功”，自然结束与恢复失败分开记录。

## 已确认参数与待取证条件

具体候选数、字节预算和时限见[H01～H04 集中确认单](19-decisions.md)。H02 参数等待与 H03 首输出等待从不同事件起算；诊断记录每段耗时及总体起播延迟。访问单元超过设备实际输入缓冲容量时，保留源数据并按策略回退，不能截断送入。顺序恢复缓存与 I03 包队列分别核算，记录额外保留的压缩包内存；D01 性能门槛只用于指定样本与输入条件。
